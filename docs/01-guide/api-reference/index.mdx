L'API de CLAIR est un serveur Fastify (`apps/api`) qui lit la base PostgreSQL par Prisma et met ses réponses en cache dans Redis. Elle est **publique, gratuite, sans authentification et en lecture seule** : l'ingestion écrit dans la base directement, pas par l'API.

---

## 🌐 Adresses

| | Production | Local |
| :--- | :--- | :--- |
| Base | `https://api.clair.vote` | `http://localhost:3001` |
| Explorateur (Zudoku) | [docs.clair.vote/api](/api) | `http://localhost:3002/api` |
| Swagger UI | [api.clair.vote/docs](https://api.clair.vote/docs) | `http://localhost:3001/docs` |
| Spécification OpenAPI | [api.clair.vote/docs/json](https://api.clair.vote/docs/json) | `http://localhost:3001/docs/json` |

Toutes les routes métier sont sous le préfixe `/api/v1`. La spécification OpenAPI est générée par l'API à partir des schémas de ses routes : c'est elle qui détaille les paramètres et les réponses de chaque route, et l'explorateur de cette documentation la lit telle quelle. L'API est aussi référencée sur data.gouv.fr : [API CLAIR, transparence politique](https://www.data.gouv.fr/dataservices/api-clair-transparence-politique).

La recherche (`/search`) passe par des requêtes PostgreSQL (`contains`, insensible à la casse), puis un classement par similarité Jaro-Winkler : il n'y a pas de moteur de recherche dédié.

## ✍️ La seule écriture publique

`POST /api/v1/feedback` enregistre un retour anonyme envoyé depuis le site, dans la table `feedbacks`. Champs : `type` obligatoire (`bug`, `idee` ou `autre`) ; `sentiment` (`positif`, `neutre`, `negatif`), `message` (2 000 caractères au plus), `email` et `page`, facultatifs. Si `FEEDBACK_DISCORD_WEBHOOK_URL` est défini, le retour est aussi notifié à l'équipe sur Discord.

## ⚙️ Autres comportements

- **Compression** gzip ou deflate des réponses de plus de 1 Ko (`@fastify/compress`).
- **En-têtes de sécurité** avec `@fastify/helmet` (politique CSP en production).
- **CORS** : en production, seules les origines listées dans `CORS_ORIGIN` sont autorisées ; en développement, toutes.
- **Nom des groupes** : l'API renvoie dans `nom` le libellé d'usage (`nom_court`) quand il existe, plutôt que le sigle figé de la source (voir [Modèle Prisma](/donnees/modele-prisma)).
- **Données non exposées** : quelques tables et colonnes ne sortent par aucune route (texte des articles, cosignataires d'un amendement, colonnes techniques, dates de naissance des candidats…). La liste exacte est sur la page [Modèle Prisma](/donnees/modele-prisma).

## 📈 Mesure d'usage

En production, l'API mesure son usage avec l'instance Plausible de CLAIR, comme le site (Plausible ne dépose pas de cookie). Chaque réponse, sauf `/health` et les requêtes `OPTIONS` et `HEAD`, envoie un événement après coup, sans retarder la réponse. L'événement contient :

- le **motif** de la route (`/api/v1/deputes/:slug`), jamais le chemin réel ni les paramètres de requête (recherches, filtres) ;
- le canal : `direct` (appel à `api.clair.vote`), `site` (visiteur relayé par le site) ou `interne` (rendu serveur, ingestion) ;
- le code de statut HTTP ;
- le nom court du client tiré de son User-Agent (`curl/8.5.0` donne `curl/8.5.0`, tout navigateur donne `navigateur`) ;
- le référent (`Referer`), quand la requête en porte un.

L'adresse IP du client est transmise à Plausible, qui s'en sert pour compter les visiteurs uniques et situer leur pays. La mesure ne s'active que si `PLAUSIBLE_EVENTS_URL` est défini ; elle est inactive en local et dans les tests.
