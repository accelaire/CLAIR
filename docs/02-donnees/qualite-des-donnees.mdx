Trois garde-fous vérifient la donnée. Ils sont à lancer après toute modification du code d'ingestion, de rattachement ou d'enrichissement, avant de fusionner :

```bash
pnpm --filter @clair/ingestion test                                    # tests unitaires (Vitest)
pnpm --filter @clair/ingestion check-quality                           # contrôles de la base
pnpm --filter @clair/ingestion exec tsx src/cli.ts check-ia-quality    # contrôles des résumés IA
```

Les deux `check-*` interrogent la base pointée par `DATABASE_URL` et sortent avec le code **1** en cas d'échec. Ne pas les faire passer dans un pipe (`| tail`, `| grep`) : le code de sortie serait celui de la dernière commande.

## 🛡️ `check-quality`

Code : `services/ingestion/src/checks/data-quality.ts`. Le contrôle réussit si **tous** les invariants et tous les seuils passent.

**Le Congrès n'a pas de votes nominatifs, c'est normal.** Les scrutins du Congrès (députés et sénateurs réunis à Versailles) sont publiés par l'AN sous un uid `VTCG…` (CG pour Congrès, AN pour Assemblée) avec leurs totaux, mais sans aucune liste de votants. Ce n'est ni une perte à l'ingestion ni un scrutin cassé : il n'y a rien à réparer. Ces scrutins sont donc exclus de l'invariant « scrutins sans aucun vote » (filtre sur `source_url` contenant `/scrutins/VTCG`), ce qui ne peut masquer aucun scrutin de l'Assemblée ni du Sénat. Au 7 octobre 2026, la base en compte un seul : `VTCGR5L16V1`, la révision constitutionnelle sur l'IVG du 4 mars 2024 (780 pour, 72 contre).

### Rapports informatifs (sans effet sur le code de sortie)

- **Intégrité des scrutins multi-amendements** : pour chaque scrutin portant sur des « amendements identiques », les numéros extraits du titre sont comparés aux amendements rattachés (manquants, en trop).

## 🤖 `check-ia-quality`

Code : `services/ingestion/src/checks/ia-quality.ts`. Il relit le champ `enjeux` des **sujets** et le résumé `resume_ia` des **dossiers**, et les confronte aux votes réels des groupes cités.

| Défaut détecté | Seuil maximal |
| :--- | ---: |
| Inversion pour/contre : un groupe décrit comme favorable alors qu'il a voté contre, ou l'inverse | 70 |
| Abstention décrite comme un vote pour ou contre | 90 |
| Position prêtée à un groupe qui n'a aucun vote sur l'entité | 20 |

Le signal « groupe pesant dans les votes mais jamais mentionné » est calculé et affiché, sans effet sur le résultat.

Les votes sont comptés sous le groupe du **mandat** à la date du scrutin, comme dans les prompts : à l'Assemblée, le mandat de la législature du scrutin ; au Sénat, le mandat en cours à sa date. Le générateur et le contrôle partagent le même fragment SQL (`services/ingestion/src/utils/groupe-epoque.ts`) : un résumé de 2018 qui cite LAREM ou LR est jugé sur les groupes de 2018, pas sur ceux d'aujourd'hui.

Les sigles successifs d'une même famille politique (FI, LFI-NUPES et LFI-NFP ; LR, UMP et DR…) sont rapprochés par leurs alias communs. LREM, le groupe du Sénat devenu RDPI, est rattaché à LAREM, car le modèle écrit « LREM » pour le groupe de l'Assemblée.

La détection des inversions repose sur des expressions régulières appliquées au voisinage de chaque nom de groupe. Elle produit des faux positifs, et ses seuils sont documentés dans le code comme des dettes à ramener vers zéro plutôt que comme des tolérances.

## 🧪 Tests unitaires

Les tests de l'ingestion (`*.test.ts` à côté des fichiers testés) couvrent notamment les parsers de sources (syceron, comptes rendus de commission, avis de commission, agenda et vidéos du Sénat, candidatures), les rattachements (débats ↔ scrutins, amendement ↔ scrutin, article ↔ scrutin), la nature des scrutins, les prompts IA et la configuration des contrôles de qualité. L'API a ses propres tests Vitest dans `apps/api/src`. Le frontend n'a pas de tests.

La CI (GitHub Actions) lance le lint, les tests et le build à chaque push et pull request sur `master`. Elle ne lance ni `check-quality` ni `check-ia-quality`, qui ont besoin d'une base remplie.
